Nesting \emph — it toggles, it doesn't just stack

Your first guide covered that a single \emph flips to upright when nested inside already-italic text. main.tex pushes this one level further with a double nesting, and the result is a genuinely useful thing to see worked out explicitly: each additional \emph layer toggles the shape relative to its immediate surroundings, rather than every \emph unconditionally meaning "italic." Two nested \emphs inside plain text therefore end up back at italic for the innermost word, having flipped twice.

source 
Some text with \emph{emphasis and
\emph{nested} content}.

Some text in \textit{italic and
\textit{nested} content}.
rendered
Some text with emphasis and nested content.
Some text in italic and nested content.

Notice the contrast in the second line: \textit nested inside \textit stays italic the whole way through — no toggling — because \textit always means "italic," full stop, regardless of context. \emph's context-awareness is precisely what makes it the right choice when you might nest emphasis; \textit's stubbornness is exactly why it's the wrong choice for that same situation.

Real bug, straight from main.tex: Some text in\textbf{bold and \textit{nested} content}. — look closely at "in\textbf": there is no space between the word "in" and the command. Because \textbf{...} starts immediately with a brace, not a letter, LaTeX doesn't get a chance to treat it as a separate word boundary, and the rendered output reads "inbold and..." with no gap — visually merging into "inbold." This is different from the well-known "commands ending in a letter eat the following space" gotcha (e.g. \LaTeX is great rendering as "LaTeXis great") — here the problem is a missing space typed by the author, not one silently consumed by LaTeX. Always leave a normal space before a command exactly as you would before any other word.

Lists — More Custom Labels

sadat_sir.tex and second_class.tex both push enumitem considerably further than the basics — one-off symbol markers mixed into an otherwise auto-numbered list, and label patterns that need an extra layer of braces to parse correctly.

One-off markers layered on top of an auto-numbered list

You don't have to choose between "every item gets a custom symbol" (enumitem's label=) and "every item auto-numbers." \item[symbol] overrides one item's marker while every other \item in the same list keeps auto-numbering normally — this is base LaTeX behaviour (as covered in your first guide), and it composes cleanly with an enumitem-customized list too.

source 
\begin{enumerate}[label=\arabic*.]
    \item System Setup
    \begin{itemize}
        \item Install software packages
        \item Configure hardware
        \item[!] Verify connections
    \end{itemize}

    \item Simulation Steps
    \begin{enumerate}[label=(\alph*)]
        \item Initialize parameters
        \item Run simulation
        \begin{itemize}[label=-]
            \item Monitor CPU usage
            \item[$\rightarrow$] Record intermediate results
        \end{itemize}
        \item Analyze outputs
    \end{enumerate}
\end{enumerate}
rendered
1. System Setup
  • Install software packages
  • Configure hardware
  • ! Verify connections
2. Simulation Steps
(a) Initialize parameters
(b) Run simulation
  • — Monitor CPU usage
  • → Record intermediate results
(c) Analyze outputs

Markers can be symbols pulled straight from math mode — \item[$\rightarrow$] needs the dollar signs even inside the square brackets, because \rightarrow only exists as a math command; forgetting the $...$ here throws Undefined control sequence.

The braces-around-a-label gotcha

Plain labels like label=\arabic*. or label=(\alph*) work without any extra wrapping. The moment your label text itself contains a command that needs its own braces — like bolding part of the label — you must wrap the entire label value in one more pair of outer braces, or enumitem's option-parser gets confused about where the label value ends and the next option begins.

source 
\begin{enumerate}[label={Step \textbf{\arabic*}:}]
    \item Parse the graphic dataset.
    \item Compile the vector graphics.
\end{enumerate}

\begin{enumerate}[label=[\Roman*]]
    \item First main objective
    \item Second main objective
\end{enumerate}

\begin{itemize}[label=$\diamond$]
    \item Specialized Diffuse Shading technique
    \item Specular Highlighting behavior
\end{itemize}
rendered
Step 1: Parse the graphic dataset.
Step 2: Compile the vector graphics.
[I] First main objective
[II] Second main objective
◇ Specialized Diffuse Shading technique
◇ Specular Highlighting behavior

The rule of thumb: if what you're writing after label= contains a brace-taking command (\textbf{}, \underline{}, ...) or would otherwise be ambiguous to parse, wrap the whole thing in { } — label={Step \textbf{\arabic*}:}, not label=Step \textbf{\arabic*}:. Note also that [\Roman*] here isn't "square-bracket syntax for roman numerals" as a special feature — the literal [ and ] characters are just part of the label text you asked for, exactly like the literal ( and ) in (\alph*) elsewhere.

Tables — Multi-line Cells, Status Color & a Live Bug

On top of multirow/multicolumn from your first guide, these files add: stacking multiple lines inside one cell, coloring a whole table's rows automatically, using color to mean something rather than just decorate — and one table that compiles perfectly while quietly rendering the wrong thing.

tabular alone vs. table + tabular together

main.tex uses a bare tabular with no surrounding table environment at all — worth being explicit about why that's a meaningfully different (and sometimes entirely appropriate) choice, not a shortcut someone forgot to finish. tabular by itself is just a grid of content — it has no caption, no number, no ability to float to a better page position, and nothing to \ref. Wrapping it in \begin{table}[htbp] ... \end{table} is what upgrades it into a numbered, captioned, cross-referenceable, page-repositionable object. Use bare tabular for a small grid that's genuinely part of the surrounding paragraph flow and doesn't need its own number; reach for the table wrapper the moment you want to write "as shown in Table 2" anywhere in your document.

\begin{tabular}{|l|l|l|}
    \hline
    \textbf{Animal} & \textbf{Food} & \textbf{Size}\\ \hline
    dog & meat & large \\ \hline
    cat & fish & small \\ \hline
    frog & flies & small \\ \hline
\end{tabular}

Multiple lines inside a single cell: \shortstack

An ordinary table cell can only hold one line of text — try to force a line break inside one with \\ and you'll break the whole row's structure instead. \shortstack[pos]{line one \\ line two} is the fix, and it's worth knowing it needs no package at all — it's built into core LaTeX. The optional [pos] (l/c/r) controls how the stacked lines align relative to each other.

source 
\begin{tabular}{|l|l|c|}
    \hline
    \textbf{Method} & \textbf{Accuracy} & \textbf{Time} \\ \hline
    Rasterization & Medium & $O(n)$ \\ \hline
    Ray Tracing &
      \shortstack[l]{High \\ Very High} &
      \shortstack[c]{$O(n^2)$ \\ $O(n^3)$} \\ \hline
    Hybrid Method & & $O(n^2)$ \\ \hline
\end{tabular}

Whole-table auto-alternating colors: \rowcolors

Your first guide covered \rowcolor{} — one command call, one row tinted. \rowcolors{start}{color-odd}{color-even} (note the extra s) is a different, table-wide tool: called once, immediately before the tabular, it automatically alternates the two given colors across every subsequent row without you touching each row individually. The start argument is which row number the alternation begins at — 2 is the usual choice, so the header row (row 1) stays untinted while the data rows alternate starting from row 2.

Color with a purpose, not just a look: this table is a good model for using color semantically — green consistently means "correct," red consistently means "needs attention" — rather than decoratively. A grader or a teammate reading the table can extract the verdict from color alone before reading a single word, which is the actual point of using color in a technical document at all.

Spot the bug: a table that compiles clean and still renders wrong

Every table mistake in your first guide threw a visible compile error — a miscounted &, a missing \\. This one from second_class.tex is a different, quieter species of bug: it compiles with zero errors or warnings, and still produces the wrong output.

source, as written (buggy) 
\begin{tabular}{|c|c|c|}
    \hline
    c11 & c12 & c13 \\
    \hline
    \multirow{2}{*}{c23} & c22 & c23 \\
    \cline{2-3}
     crash& c32 & c33 \\
    \hline
\end{tabular}
what should be there instead 
     & c32 & c33 \\
A merged cell from \multirow still needs an empty placeholder in every row it spans — as your first guide covered. The word crash was typed into that placeholder by mistake.
Why this one is worth internalizing: the table declares exactly 3 columns, and the buggy row (crash & c32 & c33) still has exactly 3 cell-slots — so LaTeX's column-count check, which is what normally catches multirow mistakes, has nothing to object to. The word "crash" isn't an extra column; it's content sitting where blank space was supposed to be, directly underneath the merged c23 cell above it. The lesson: not every LaTeX bug throws an error message. Some just quietly produce the wrong PDF, which is exactly why comparing your compiled output against what you actually intended — not just checking "did it compile" — has to be part of every table you build.

Figures — Wrapped Figures & the Subfigure Line-Break Rule

sadat_sir.tex is the most disciplined of all your files about figures — it comes with its own teaching-note table for float placement and an explicit, bolded, red-text warning about the single most common subfigure mistake.

Text-wrapped figures: wrapfigure

Every figure you've seen so far claims the full paragraph width, forcing text to stop, the image to appear, then text to resume below it. wrapfigure (from the wrapfig package) does something structurally different: it lets body text flow around a small image sitting in the margin of the same paragraph, the way a magazine or newspaper column often does.

source 
\begin{wrapfigure}{r}{0.36\linewidth}
    \centering
    \includegraphics[width=\linewidth]{padma_river.jpg}
    \caption{Wrapped image.}
    \label{fig:wrapped-padma}
\end{wrapfigure}

A wrapped figure lets text flow beside
an image...
what the two arguments mean
First argument (r): which side of the text the image sits on — r right, l left (also i/o for "inside/outside" in double-sided documents that print on both faces of the page).

Second argument (0.36\linewidth): how wide the wrapped box is — this is not optional the way a plain figure's width is, since text needs to know exactly how much horizontal space to leave.
Practical sizing advice, straight from the source file: keep a wrapped image between roughly 0.25\linewidth and 0.40\linewidth. Too narrow and the wrapped text column becomes an unreadable sliver; too wide and there's no room left for text to actually wrap around. Also leave enough body text after the wrapped figure — if the paragraph ends too soon, the next section's heading can end up awkwardly close to, or overlapping, the tail end of the image.

The subfigure rule your teacher put in bold red text

This is emphatic enough in the source material that it deserves the same treatment here. Building on the "blank line starts a new row" mechanic from your first guide's asymmetric-layout example — that mechanic is a deliberate tool when you want it, and an accidental trap when you don't.

WARNING (verbatim from the source): "Do not put a blank line between subfigures. It starts a new paragraph, and forces the next subfigure onto a new line, no matter the sizes." Two subfigures set to 0.45\linewidth each, separated only by \hfill with no blank line between them, sit side by side correctly. The exact same two subfigures with an accidental blank line between them — often just an extra press of Enter while editing — silently break onto two separate rows instead, even though their widths would have fit comfortably side by side. Because this produces no error at all, it's a purely visual bug you only catch by actually looking at the compiled PDF.

hyperref, nameref & autoref

lab_practice.tex exercises a noticeably richer cross-referencing vocabulary than plain \ref — plus, right at the top, a genuine duplicate-label bug worth learning to recognize.

\hyperref[label]{custom text} — a clickable link with your own wording

Plain \ref{} only ever gives you a bare number. When you want a clickable cross-reference whose visible text is something other than just that number — "Akif's legendary GOAT status" instead of "Figure 1" — \hyperref[label]{text} (square brackets around the label, curly braces around your custom text) is the tool, and it needs hyperref loaded.

\nameref{} — the section's actual title, not its number

\nameref{label} prints the title text of whatever sectioning unit that label points to, rather than a number — useful for "jump back to the X guide" phrasing where the number alone ("see Section 2") is less helpful to a reader than the words ("see the Modifying Texts guide").

\autoref{} — the reference labels itself for you

Writing "Figure~\ref{fig:x}" or "Equation~\eqref{eq:y}" by hand every single time means typing the right noun yourself and keeping it consistent across a whole document. \autoref{} inspects what kind of thing the label points to — figure, section, equation, table — and automatically prepends the matching word for you, so \autoref{fig:trump} alone produces "figure 3," no manual "Figure~" needed.

source 
In \autoref{fig:trump}, we can see...
\autoref{eq:euler} is Euler's identity.
rendered
In figure 3, we can see... equation 1 is Euler's identity.
The gotcha almost everyone hits: \autoref's built-in names are lowercase by default — "figure 3," not "Figure 3" — which surprises people expecting a capital letter, especially at the start of a sentence. Fix it once, globally, in the preamble by redefining the specific autoref-name command for each type you care about: \renewcommand{\figureautorefname}{Figure}, \renewcommand{\equationautorefname}{Equation}, and so on (the pattern is always \<type>autorefname).

Spot the bug: a label defined twice

lab_practice.tex has this exact line appearing twice, once in §2 and again, verbatim, in §5:

Here you can see we can refer \ref{fig:akif_cg_4}\label{Picture}
from a different place
! LaTeX Warning: Label `Picture' multiply defined.

Every \label in a document must be unique — it's how LaTeX knows which single numbered thing you mean when you later \ref it. Defining Picture twice doesn't stop the document from compiling, but it does mean any later \ref{Picture} resolves to whichever one of the two definitions happened to be processed last, silently — LaTeX warns you in the compile log, but says nothing in the actual PDF, so this is exactly the kind of bug that survives unnoticed in a final submission unless you actually read your compile warnings.

Also worth noticing: this particular \label{Picture} is attached to a sentence, not to a figure, table, or section — so even correctly used and made unique, it wouldn't have a meaningful number to report; \label only captures a number from the most recently updated counter, and plain body text doesn't update any counter at all.

Math — Custom Operators & Real-World Formulas

second_class.tex's math section reads like a mini reference sheet for physics and engineering notation, and sadat_sir.tex adds one more tool your first guide's Math sections didn't cover: defining your own named operator.

Defining a custom operator: \DeclareMathOperator

Your first guide's §07 covered the built-in roman-type operators (\sin, \lim, \det, ...) — upright text, correctly spaced, instead of a cramped italic product of letters. \argmax isn't one of the built-ins, but you're not stuck writing it by hand every time either: amsmath's \DeclareMathOperator lets you register your own, in the preamble, once.

preamble 
\DeclareMathOperator*{\argmax}{arg\,max}
breakdown
\argmax — the new command name you're creating.

arg\,max — the upright text it prints; the \, thin space keeps "arg" and "max" from crowding together the way two touching words normally would in upright math text.

The star on \DeclareMathOperator* is the whole point here: it makes a subscript like \argmax_{x} stack directly underneath the operator in display math — exactly like \max or \lim do — instead of squeezing to the side as a small subscript. Drop the star and you get the side-squeezed version instead.
Common mistake: calling \DeclareMathOperator inside the document body, or worse, inside a math environment itself. It's a preamble-only declaration — like \newcommand or \newtheorem, it defines a new command for later use and must be issued before \begin{document}.

Footnotes, Verbatim & Typewriter Text requested

The last two lines of sadat_sir.tex are comments asking directly for this: "please teach me how to use \texttt ... also teach me how to use \verbatim." Both, plus a neat footnote-reuse trick from the same file, are here.

\texttt{} — typewriter text, in depth requested

Your first guide introduced \texttt{} in one line as part of the font-family trio (\textrm/\textsf/\texttt); here's the fuller picture. \texttt{...} switches the enclosed text to a fixed-width (monospace) font — every character occupies the same horizontal space, the way code actually looks in an editor. It does not disable LaTeX's interpretation of special characters the way verbatim commands do — \texttt{} is purely a font change, and its argument is still ordinary LaTeX text, meaning a stray % or _ inside it still needs the usual escaping (\%, \_) or it will still break.

source 
Image insertion needs the
\texttt{graphicx} package. A path
might look like \texttt{images/fig1.png}.

\% and \_ still need escaping even
inside \texttt{}: \texttt{50\% done,
file\_name.py}
rendered
Image insertion needs the graphicx package. A path might look like images/fig1.png.

% and _ still need escaping even inside \texttt{}: 50% done, file_name.py

Typical uses: package names, file names and paths, command names in running prose (as this whole guide does with \texttt{}-style spans throughout), directory structures, or any short technical token you want to visually distinguish from ordinary prose without necessarily making it "code" in the fuller sense that \verb or \lstlisting imply.

\verb|...| — inline literal text requested

The problem \verb solves: sometimes you want to show LaTeX source code itself as text on the page — \textbf{...}, backslashes and all — without LaTeX actually interpreting it as a command. Wrapping \textbf{...} in \texttt{} doesn't achieve this; \textbf would still be executed as a real bolding command, it would just be typeset in monospace font while doing so. \verb is fundamentally different: it disables LaTeX interpretation entirely for its argument and prints the exact characters you typed, verbatim, in typewriter font.

source 
Use \verb|\textbf{...}| to make
text bold.

You can also delimit with a
different character, e.g.
\verb!100% correct!, if your
content itself contains a
vertical bar.
rendered
Use \textbf{...} to make text bold.

You can also delimit with a different character, e.g. 100% correct, if your content itself contains a vertical bar.

\verb takes its delimiter from whatever character immediately follows it — almost always | by convention, but any character not appearing inside the content works, which matters the moment your snippet itself contains a literal |. Two hard rules: the opening and closing delimiter must match, and \verb is "fragile" — it cannot be used inside the argument of most other commands (for instance, directly inside a \footnote{} or a section title) without special handling, because those commands process their arguments in a way that conflicts with \verb's own special character-reading mode.

\begin{verbatim} — the block-level version requested

Same underlying idea as \verb, extended to multiple lines: everything between \begin{verbatim} and \end{verbatim} is printed exactly as typed — line breaks, spacing, indentation, and all special characters included — with zero LaTeX interpretation. This is the environment your first guide's Package Starter Kit blocks and every code-ish snippet in these two guides are actually built from, structurally.

source 
\begin{verbatim}
def greet(name):
    return f"Hello, {name}!"
\end{verbatim}
rendered 
def greet(name):
    return f"Hello, {name}!"
ToolScopeBest for
\texttt{}Inline, interprets LaTeX normallyShort technical tokens (filenames, package names) inside a sentence.
\verb|...|Inline, disables interpretationShowing a short piece of literal LaTeX/code source mid-sentence.
verbatimBlock, disables interpretationA whole multi-line code snippet on its own.

Which one to actually reach for: if you just need a plain, undecorated block of literal text or simple code, verbatim is completely sufficient and needs no extra package. The moment you want color-coded keywords, line numbers, or a numbered caption you can \ref — as you will for any real Python code in an assignment — that's exactly the gap lstlisting (§10) exists to fill.

Bonus: citing the same footnote twice

Not requested in the comments, but a genuinely useful trick sitting right next to them in the same file. An ordinary \footnote{} always creates a new numbered note. To point a second reference back at a footnote you already wrote, give that footnote its own \label and reuse the number with \footnotemark:

First mention.\footnote{\label{fn:tool}A repeated note.}
Second mention.\footnotemark[\ref{fn:tool}]

The first line both prints the note text and labels its number. The second line prints only a matching superscript number — no new note text at the bottom of the page — pointing back at the same footnote via \ref.

Algorithms & Pseudocode

Not in your first guide at all — sadat_sir.tex demonstrates a full binary search written as properly numbered, captioned pseudocode. This is the standard way to present an algorithm in a CSE report rather than pasting real code and calling it pseudocode.

Two packages, two jobs

algorithm and algpseudocode divide the work the same way table and tabular do. algorithm provides the outer float — numbering, a caption, a label, the ability to \ref it, and placement specifiers exactly like a figure or table. algpseudocode provides the inner vocabulary — the actual keywords (\State, \While, \If, ...) used inside an algorithmic block to write the steps themselves.

source 
\begin{algorithm}[H]
    \caption{Binary Search}
    \label{alg:binary-search}
    \begin{algorithmic}[1]
        \Require Sorted array $A$, target value $x$
        \Ensure Index of $x$, or $-1$ if not found
        \State $low \gets 1$, $high \gets n$
        \While{$low \leq high$}
            \State $mid \gets \lfloor (low + high)/2 \rfloor$
            \If{$A[mid] = x$}
                \State \Return $mid$
            \ElsIf{$A[mid] < x$}
                \State $low \gets mid + 1$
            \Else
                \State $high \gets mid - 1$
            \EndIf
        \EndWhile
        \State \Return $-1$
    \end{algorithmic}
\end{algorithm}
what each piece means
[H] on algorithm — same placement specifier as figures/tables (§04), requires float.

[1] on algorithmic — turns on line numbers, numbering every line (a [5] here would number every 5th line instead).

\Require/\Ensure — the algorithm's stated pre- and post-conditions, printed as a labelled header block before the steps begin.

\gets — renders as ← (assignment), the pseudocode convention distinguishing "assign" from mathematical equality.

\State — a generic single step; everything that isn't a control-flow keyword is wrapped in one of these.

\While{...}...\EndWhile, \If{...}...\ElsIf{...}...\Else...\EndIf — control structures; every opener needs its matching \End..., the same discipline as \begin/\end for environments.

Once wrapped in the algorithm float, it's referenceable exactly like any other numbered object: Algorithm~\ref{alg:binary-search} in running prose, same mechanism as a figure or table reference.

The rest of the control-flow vocabulary

CommandProduces
\For{...} ... \EndForA for-loop block, e.g. \For{$i = 1$ to $n$}.
\ForAll{...} ... \EndForA "for all" loop, common in set/array-processing pseudocode.
\Function{Name}{args} ... \EndFunctionDefines a named sub-procedure block, callable from elsewhere in the same or another algorithm.
\Comment{text}An inline pseudocode comment, visually distinguished from actual steps.

Code Listings — Importing Python Code requested

The other half of your sadat_sir.tex comment request: "import a python code as \listing." The listings package is exactly this tool — a source-code-aware version of verbatim with syntax highlighting, line numbers, and float-like captioning built in.

Step 1 — configure the look once, in the preamble

\lstset{...}, called once in the preamble, sets the default appearance for every lstlisting block in the whole document, so you don't repeat the same styling options at every single code block.

preamble (from sadat_sir.tex) 
\usepackage{listings}
\usepackage{xcolor}   % for the custom colors below

\definecolor{customblue}{RGB}{0, 76, 153}

\lstset{
    basicstyle=\ttfamily\small,
    keywordstyle=\color{customblue}\bfseries,
    commentstyle=\color{teal!70!black},
    stringstyle=\color{red!70!black},
    frame=single,
    breaklines=true,
    showstringspaces=false,
    columns=fullflexible
}
what each option controls
basicstyle — the font for ordinary code text (monospace, small, here).

keywordstyle/commentstyle/stringstyle — separate colors/weights for language keywords, # comments, and string literals — this is where the syntax-highlighting colors actually come from.

frame=single — draws a box around the whole listing.

breaklines=true — wraps long lines instead of letting them run off the page edge.

showstringspaces=false — stops listings from visually marking spaces inside string literals with a special glyph, which looks noisy for ordinary prose-like strings.

columns=fullflexible — a spacing-metric option that generally makes monospaced text look less cramped/uneven.

Step 2 — write the actual listing

source 
\begin{lstlisting}[language=Python,
  caption={A small Python function.},
  label={lst:python-square}]
def greet_user(name):
    # Create a greeting message
    message = f"Hello, {name}! Welcome to Python."

    # Print the greeting message
    print(message)

    return message


user_name = "Alice"
greet_user(user_name)
\end{lstlisting}
rendered 
def greet_user(name):
    # Create a greeting message
    message = f"Hello, {name}! Welcome to Python."

    # Print the greeting message
    print(message)

    return message


user_name = "Alice"
greet_user(user_name)
Listing 1: A small Python function.

language=Python is what tells listings which keyword set to actually highlight — def, return, import, and so on all get keywordstyle's color specifically because listings recognises them as Python syntax; the same source with language=C would highlight a completely different keyword set. Notice caption and label are given directly as options to lstlisting itself, not via a separate outer float environment the way a table needs \begin{table}...\end{table} around a tabular — lstlisting is self-floating, and immediately referenceable afterward as Listing~\ref{lst:python-square}.

A note on alternatives: you may also encounter the minted package, which uses the external Pygments highlighter and generally produces nicer-looking output than listings. The trade-off is that minted requires -shell-escape to be explicitly enabled at compile time (it shells out to a Python program), which many shared or restricted LaTeX environments — including a typical classroom Overleaf setup — don't allow by default. listings needs nothing beyond the package itself and compiles anywhere, which is exactly why it's the safer default for coursework.

Inserting an existing .py file directly, without retyping it

If your Python code already exists as its own file rather than being typed inline, listings can pull it in directly rather than you copy-pasting (and risking a transcription mistake):

\lstinputlisting[language=Python,
  caption={Imported from an external file.},
  label={lst:external}]{code/my_script.py}

The path is relative to your .tex file's location, exactly like an image path in \includegraphics. This is the single most reliable way to guarantee the code shown in your report exactly matches a script you actually ran — there's no manual retyping step where a copy error could sneak in.

Two-Column Documents

Mentioned in sadat_sir.tex as a separate companion demo rather than shown inline — the concept is short enough to cover fully here.

\documentclass[twocolumn]{article}
...
\begin{figure*}[t]
    \centering
    \includegraphics[width=0.9\textwidth]{wide_diagram.png}
    \caption{A figure spanning both columns.}
\end{figure*}

[twocolumn] as a document-class option switches the entire document to a two-column layout — text automatically flows down the first column, then continues at the top of the second, the way a newspaper or a conference paper is typically laid out. An ordinary figure or table inside a two-column document is confined to the width of just one column, which is often too narrow for a wide diagram. The starred variants, figure* and table*, break out of that constraint and span the full page width across both columns — at the cost of only accepting t or b placement (top/bottom of a page), never h, since a full-width float physically cannot sit "here" in the middle of one narrow column.

The Preamble Bug & a Debugging Checklist

The single most instructive bug across all eight files you've shared so far is sitting in second_class.tex's opening lines — worth its own section rather than a quick callout.

Content before \begin{document}

source, exactly as written (buggy) 
\newtheorem{theorem}{Theorem}
\newtheorem{lemma}[theorem]{Lemma}

\maketitle
\newpage
\tableofcontents
\newpage
\begin{document}

\section{Introduction}
    ...
what actually happens
! LaTeX Error: Missing \begin{document}.

This is one of the most instantly recognizable error messages in LaTeX, and it means exactly what it says.

The distinction that matters: the preamble — everything between \documentclass{} and \begin{document} — is only allowed to contain declarations — things that configure or define, but don't themselves produce visible output. \usepackage{}, \title{}/\author{}/\date{} (which only store values, as your first guide's §03 covered), \definecolor{}, \newcommand{}, and \newtheorem{} all genuinely belong here — none of them puts a single mark on a page by itself. \maketitle, \tableofcontents, and \newpage are a fundamentally different category: they typeset — they produce actual content and page breaks — and typesetting can only happen once \begin{document} has run its internal setup (initializing the page-building machinery, applying the base font size, establishing the output routine). Move all four lines below \begin{document}, in the same relative order, and the error disappears.

Why this specific mistake is common: in an earlier, simpler file (or a different day's practice), it's easy to build the habit of writing \maketitle and \tableofcontents "near the top" of the file without consciously tracking whether that's above or below \begin{document} — especially once \newtheorem declarations (which genuinely do belong in the preamble) are sitting right next to them, creating the illusion that everything in that opening block is preamble material.

A debugging checklist, adapted from sadat_sir.tex

SymptomLikely fix
A reference shows as ??Compile again — LaTeX needs a second pass to resolve labels (§05, and your first guide's §03/§09).
A citation shows as ?Check the citation key spelling against the .bib file, and confirm the full pdflatex → bibtex → pdflatex → pdflatex cycle actually ran.
An image is missingCheck the file name, extension, and folder path exactly — these are case-sensitive on most systems even when your OS isn't.
A float has drifted far from where you placed itTry [!htbp] before reaching straight for [H] — §04.
A subfigure row overflows the page widthReduce each subfigure's width fraction first, before adding manual spacing — two subfigures should sum to noticeably less than 1 (§04, and your first guide's §05).
Colored table cells don't workConfirm \usepackage[table]{xcolor} specifically — plain xcolor without the table option won't recognise \rowcolor/\cellcolor (§00, and your first guide's §00/§04).
